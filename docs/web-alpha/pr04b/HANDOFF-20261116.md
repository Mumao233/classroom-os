## 1. 结论

删除受理、访问撤销、对象物理清除、到期清扫、孤儿清扫和备份恢复流程已实现并在真实 PostgreSQL 17.11 与 SeaweedFS 4.53 上通过故障注入验证。以下四项没有完成，合并前需要知情：

0. **独立复审第 2 轮仍有两条高严重度问题未修复**（第 8 节）：多进程并发重放级联时可能多删；恢复流程未隔离副本中的可调度任务。两轮修复额度已用尽，是否追加一轮由用户决定。
1. **数据库正文清除未实现。** 课堂、课程、学期、账户范围的删除在对象清除完毕后保持 `pending_delete`，不报告为已删除（第 5 节 R1）。
2. **账户禁用与凭据撤销未写入独立日志。** 恢复流程要求操作者显式声明备份之后失去访问权的账户（R2）。
3. **保留期限与备份策略未定。** TBD-04、TBD-05 未签署，本包没有替产品决定任何数值，音频提交保持关闭。

## 7. 对后续工作包的交付

### PR-05b（原音保留与提交）

- 保留期限的唯一权威是 `retention_policies`。TBD-04 签署后插入已批准的版本行（`version`、`media_kind`、`max_lifetime`、`approval_reference`），资产引用该版本并带齐 `first_cloud_received_at`、`retention_anchor_at`、`expires_at`、`hard_expire_at`。触发器拒绝未批准的版本、缺失或超限的期限，分配后不可更换。
- 开放音频提交需要以新迁移替换 0009 的 `media_audio_commit_not_enabled`。本包没有动它。
- 到期由 `DeletionService.expire_due()` 处理，需要由调度方周期调用；本包没有注册定时任务。
- 原音删除入口为 `audio` 范围，只清除该课堂的 `audio_chunk`，课堂与文字保留。

### PR-06c（读取与可用性）

- 读取路径继续使用既有的墓碑与媒体状态检查，本包没有新增读取侧接口。到期瞬间的拒读由 04a 的检查完成，清扫只负责随后的撤权登记与物理清除。
- 课堂被撤销后，`get_class_session` 抛出 `Gone`，媒体访问返回 410。

### PR-08a（同步与事件）

- 事件类型 `object.deleted`，载荷为 `object_type`、`object_id`、`deletion_id`、`state`，`state` 取 `access_revoked`、`pending_delete`、`delete_failed`、`deleted`，经既有 outbox 与 owner 序号发布。
- 级联只为根对象发事件。后代的撤销由祖先墓碑表达，客户端需按父子关系推导。
- 含数据库正文的范围目前不会发出 `deleted`（R1）。

### PR-08c（导出与导入）

- 导出产生的对象只要登记为 `media_assets` 行（`kind='export'`）并挂在课堂下，就自动进入该课堂及其祖先的删除清单，无需额外登记。
- 不挂课堂的对象只被账户范围覆盖。若导出需要独立的删除范围，应增加范围类型并在 `classroom_web_deletion_scope` 中定义，而不是绕过清单。
- 清单按对象键登记，键必须是 04a 的生成格式。

### PR-11b（运维与计量）

- 健康与审计：`classroom_web_deletion_audit()` 返回 `exposed_media`、`unaccepted_requests`、`open_requests`、`failed_requests`、`content_erasure_outstanding`、`erasing_accounts`，由 worker 或恢复身份调用。前两项非零时服务不应开放。
- `DeletionService.ready` 为假时全部 API 返回 503 `SERVICE_DISABLED`。启动顺序必须先 `reconcile()`。
- 需要告警的情形：`failed_requests` 持续非零、`reconcile()` 报告 `unresolved`、日志抛出 `LedgerCorrupt`。
- 每次备份时记录 `S3DeletionLedger.head()`，保存在日志存储之外。

| P1 | `application/deletion.py` `RestoreCoordinator.run()` | 恢复流程没有隔离副本中的可调度任务就判定可开放 | 备份里某任务处于排队状态，而它在备份之后已提交给供应商 | 恢复时隔离可调度任务，核对提交状态后再开放。需要任务层与计费层（02b、11a）提供接口，设计第 7 节有此要求 |
| P2 | `application/deletion.py` `_apply()` | 到期意图的 owner 不在副本中时，写请求行违反外键，被记为未解决 | 备份早于某账户创建，该账户的媒体后来到期并进入日志 | 调用到期函数前先识别 owner 不存在，按已覆盖处理 |
| P2 | `application/deletion.py` `reconcile()` | 先读日志、后读数据库，两次读取之间另一进程受理的删除会被误判为日志落后 | 多进程部署下对账与受理并发 | 先读数据库再读日志，或发现更新的本地代数时重读日志 |
| P2 | `deletion_ledger.py` `entries()` | 全链读取在内部锁之外进行，与同一实例上的追加并发时会误报历史被改写 | 同一进程内 `entries()` 或 `head()` 与追加并发 | 全链校验期间持有内部锁，或在缓存合法前进时重试 |

后三条的后果都是误判后保持关闭，不会造成数据暴露或多删。前两条是高严重度：第一条在多进程并发重放时可能多删，第二条可能在恢复后重复提交任务。两条都只在备份恢复或崩溃重放时触发，正常受理路径不受影响。
