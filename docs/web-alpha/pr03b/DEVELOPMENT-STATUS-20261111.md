## R05：本轮重新核实的方案冲突

本轮 `inspect_remaining.py` 只读读取当前正式迁移和原分析方案，并核对本次 PG JUnit；输出 [REMAINING-PREREQUISITES.json](../../../outputs/pr03b/f02-context-20261111-01/REMAINING-PREREQUISITES.json)，附精确源码摘要。

1. 当前 `0007_authentication.sql` 的 account_fail 为 **3 次/900 秒**；匿名 preauth 为 **300 秒**。本轮真实 PG 用例 `test_three_failure_budget_is_shared_across_fresh_protocol_contexts` 仍通过：前三次 401，第四次 429，实际 hash 调用总数 3；更换 preauth 不清预算。
2. 原采样方案要求同一目标 admitted k=4，同时要求同一八请求序列只能使用一个真实 preauth、不允许更换。预算不耗尽前最多只有 3 次昂贵验证。
3. 等待 900 秒自然恢复也不能原样满足该方案：原 preauth 在 300 秒即过期。重置预算、延长 preauth、换目标拼接、删掉 k=4 或只统计有利分层，都不属于本次可自行采取的修复。
4. readiness 因容量前置未整体通过、admitted k4 与硬预算冲突、完整 collector 未实现/验证，明确拒绝启动。432000 个独立 arm 序列/3456000 次请求只是原下限，不是能满足同时置信上界的充分样本量。

这是验收方法与实际限制的冲突；现有证据没有证明认证可枚举或不可枚举，也不是放宽生产预算的理由。已按“出现重大问题”保留整包未通过，不用再跑一轮相同短测填补它。
