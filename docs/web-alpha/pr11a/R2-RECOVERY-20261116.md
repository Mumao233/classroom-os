## 缺陷与最小修复

`TaskWorker` 在 `store_result` 的事务提交后才调用 usage/费用回调。若进程此时硬退出，或 `usage_for` / `billing.completed` 抛错，raw result 已持久化而费用仍为 submitted。旧恢复逻辑发现 raw result 后重新排队、清空租约，下一轮跳过供应商提交并发布本地结果。原 `sync_execution` 没有识别恢复后的 queued 和最终 succeeded 等状态，租约又已清空，因而长期把未确认费用保留为正常 held。维护轮询重复调用同一同步逻辑也不能修复。

生产修复只修改 `web/backend/classroom_web/infrastructure/billing_repository.py:71` 附近的一个状态分支：submitted 遇到 queued、unknown、succeeded、failed、cancelled 时转 unknown。原撤权、过期租约和取消判断保留。任务重新排队或输出已发布，均不能证明最终 usage 已结算。

这个转换复用原事务、锁、元数据函数和 exposure 同步；没有新增任务正文权限、DDL、契约字段或供应商请求。恢复仅将剩余 held 风险移入 unknown，保留已知实际费用。迟到最终 usage 继续使用原幂等结算端口。判断只作用于 submitted，已有 settled 不会因恢复、维护轮询或缺失 usage 回调而回退。

硬退出用例由独立进程运行真实 `TaskWorker`。模拟 submit 写入并 fsync 调用记录，`usage_for` 使用 `os._exit(73)`，跳过 finally；父进程断言退出 73、仅一次调用，并从另一 PG 连接读取已提交的 pending raw result，再使租约过期。其余两种中断分别在 usage 与结算回调抛出异常，均在结果持久化后发生。

worker 路径断言恢复为 queued 时费用即为 unknown，随后发布成功仍保持 unknown。维护路径让原已存结果恢复/发布在没有即时费用 hook 的情况下完成，再由真实受限 `recover_pending` 修复为 unknown。两条路径均验证 held=0、unknown=100、settled=0，只有一个 attempt，恢复期间无新 usage、无供应商重发或查询。迟到最终 usage=40 连续递交两次只产生一条回执，风险归零、settled=40；后续同步、空 usage 回调和轮询不回退。

修复前快照使用同组 8 个用例；最终用例额外显式检查了 queued 中间状态，没有放宽旧断言。已 settled 的成功/无效输出两种恢复场景也直接校验金额及状态保留。上述数值都是合成参数。
